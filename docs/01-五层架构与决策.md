# 通用测试框架 —— 可行性分析与决策建议

> 依据：起源系统(Origin) 多轮迭代回归测试实践+ e2e 框架源码分析 ｜ 2026-10-03
> 目标：为后续 CRM / MES / ERP 等 B 端系统建立统一测试能力

---

## 先盘点：起源系统(Origin)测试到底沉淀了什么

把长期实践拆开看，资产分两类——**可跨系统复用的工程能力（约 60%）** 与 **财务域独有知识（约 40%）**：

| 资产 | 类别 | 复用方式 |
|---|---|---|
| 角色 token 矩阵 + demo-login | 工程 | 直接复用 |
| req() 封装 + 错误码语义断言（400/403/409 × code） | 工程 | 直接复用 |
| 基线四步法（前置快照→测试→还原→终态校验） | 工程 | 直接复用 |
| 勾稽断言原语（diff=0 / A=B / 双向Δ / allMatched） | 工程 | 直接复用 |
| 旅程穿行结构（J0'~J9） | 工程+领域 | **模板化后泛化**（见下） |
| 报告三段式（发现→证据→建议）+ saga 追踪 + 缺陷编号 | 工程 | 直接复用 |
| 三通道方法论（REST / MCP tools-call / UI-e2e） | 工程 | 直接复用 |
| 复式平衡 / 结账锁 / FIFO / 净额结转… | **财务领域** | 换系统重写 |
| AUX/TAX/FA 用例编号体系 | **财务领域** | 换系统重写 |

**关键观察**：J0'~J9 旅程骨架本身就是泛化的 B 端系统测试形态——

```
越权与多租户 → 主数据建账守卫 → 档案域 → 业务单据循环(多线)
→ 周期性关账(状态机锁定) → 报表勾稽 → 跨期承接 → 审计穿透
```

CRM = 线索→商机→合同→回款→业绩关账；MES = 工单→报工→质检→入库→批次冻结；ERP 与起源系统(Origin)近亲。**骨架同构，领域步骤不同**——这正是"框架 + 领域插件"的分界线。

---

## 问题一：可能性

**结论：高度可能，且我们已持有 70% 的实践原型——起源系统(Origin)测试无意中长出了框架的全部雏形，缺的只是把"脚本习惯"提炼成"框架约束"。**

三个论据：

1. **实践论据**：EPF 纲要（开发侧）与我们的断言体系（测试侧）在起源系统(Origin)上已经跑通了"三层合流"（域级 622 用例 CI / 穿行层 / 工具通道）——这本来就是框架的运行形态，只是没有产品化。
2. **结构论据**：B 端系统测试骨架同构（上表）；e2e 源码证实 UI 层可以买现成的（Apache-2.0），不必自研浏览器自动化。
3. **反例约束（诚实预期管理）**：起源系统(Origin)测试约 40% 的价值来自会计域知识（知道 3103 该承接多少、FIFO 该跳过耗尽层）。**框架解决"怎么跑"，永远解决不了"测什么"**——领域测试设计每个系统仍需人力投入，框架的承诺是把它从 3 周压到 1 周，而不是压到零。

**风险**：现在只有一个系统样本（n=1），直接做"通用框架"有过度设计风险——财务特有的抽象（结账锁、复式平衡）可能被误当成通用概念。对策见决策部分的三步走。

## 问题二：需要设计/开发侧提供的前提（可测性契约）

这是成败关键。起源系统(Origin)测试中我们**被迫逆向**的一切，就是前提清单——每一条都有本项目的血泪证据：

| 级别 | 前提 | 起源系统(Origin)实况（代价） | 形式要求 |
|---|---|---|---|
| **P0** | **API 契约**（OpenAPI/TS 类型） | 靠 Vite 源码明文+报错提示逐个逆向（发票 relationType、印花税 items…浪费大量轮次） | 每系统交付 OpenAPI spec，测试脚手架自动生成 |
| **P0** | **错误码枚举清单** | SELF_AUDIT_DENIED 等语义断言是高效基础，但靠摸索 | code 全局唯一 + 枚举文档（起源系统(Origin)做得好，直接抄） |
| **P0** | **角色 × 权限矩阵测试账号** | demo-login R01~R06 是整个 RBAC 测试的地基 | 交付时附账号-权限点矩阵表 |
| **P1** | **环境重置/种子数据版本化** | 最大痛点：无重置机制，跨轮污染只能"不逐字节回滚"，基线漂移要人工识别（15,200↔14,524 事件） | 重置 API 或快照回滚；种子数据带版本号 |
| **P1** | **业务不变量清单** | 四路勾稽/日记账=1002/3103 承接，全靠测试侧领域理解反推 | 设计侧交付"不变量表"（哪些量必须相等/守恒），哪怕一张表 |
| **P2** | **MCP 工具面** | 起源系统(Origin) 43 工具通道 = 测试免费获得 agent 能力 | 延续"系统即 MCP 服务器"路线 |
| **P2** | **时间/状态可测性开关** | "次月起提"靠真实月份等待，成本极高 | test-mode 时间控制、状态跃迁强制入口 |

**一句话：P0 三条不满足，测试只能继续"考古式"进行，框架无从谈起；P1 决定框架效率上限。**

## 问题三：架构设计

### 借鉴对象取长补短

| 框架 | 借什么 | 不抄什么 |
|---|---|---|
| **e2e** | 三层断言（locator/agent+回放缓存/API）、session 管理、失败快照 artifacts | UI 中心主义（我们 REST/MCP 为主） |
| **Playwright** | fixture 依赖注入、trace viewer | — |
| **pytest** | 插件体系、conftest 分层、参数化 | python 单语言绑定（见技术栈决策） |
| **Schemathesis** | 契约驱动生成用例 | 只测 API 不测旅程 |
| **我们自己（EPF）** | 旅程结构、基线四步、报告三段式 | 脚本形态（要产品化） |

### 五层架构

```
┌────────────────────────────────────────────────────────┐
│ L5 报告层   发现→证据→建议 · saga 追踪 · HTML 汇报      │
│            · 缺陷编号 · 覆盖率矩阵(方法×模块×用例)      │
├────────────────────────────────────────────────────────┤
│ L4 旅程层   泛化 EPF 模板: 越权→主数据守卫→档案→       │
│            业务循环→周期关账→报表勾稽→跨期→审计        │
│            (每系统一份 journeys 实例 = 领域插件)        │
├────────────────────────────────────────────────────────┤
│ L3 原语层   错误码语义 · 勾稽(diff=0/A=B/双向Δ) ·      │
│            状态机 · 幂等防重 · 基线四步管理器           │
├────────────────────────────────────────────────────────┤
│ L2 通道层   REST(角色token) · MCP(tools/call) ·         │
│            UI(内嵌 e2e 项目) —— 同一断言多通道交叉      │
├────────────────────────────────────────────────────────┤
│ L1 契约层   OpenAPI 解析 · 错误码枚举 · 不变量表 ·      │
│            角色矩阵 —— 输入=P0/P1 前提,输出=脚手架      │
└────────────────────────────────────────────────────────┘
```

六个核心设计决策：

1. **契约驱动（L1 是根）**：OpenAPI + 错误码枚举进，60% 测试骨架代码出。设计侧给契约的质量直接决定测试效率。
2. **三通道统一 API**：`probe('创建订单').via('rest'|'mcp'|'ui')` —— 起源系统(Origin) J9"四层穿透"的产品化；UI 通道不重造轮子，直接编排 e2e。
3. **旅程模板 = 泛化 EPF**：框架内置 B 端通用旅程骨架（9 段），每系统实例化步骤与断言。这是最大复用资产。
4. **基线管理器**：自动快照/还原/终态校验（把起源系统(Origin)手工四步自动化），依赖 P1 环境重置前提；无重置能力时降级为"漂移检测告警"（e2e 回放三态思想的移植）。
5. **Agent 步骤可选层**：复杂路径 `agent.act()` 录制→零模型回放→变更接管（e2e 缓存机制）；模型可插拔；甚至执行者本身就是 Claude 会话（框架产出结构化任务清单，agent 驱动）——起源系统(Origin)模式的正式化。
6. **报告即产品**：L5 直接产出我们已验证的报告形态（本轮 HTML 汇报的自动化版），给管理层和开发各取所需。

### 技术栈决策点（需拍板）

| 选项 | 优势 | 代价 |
|---|---|---|
| **A. TypeScript**（推荐） | 与 e2e 同生态；OpenAPI→TS 类型自动生成；前后端共享契约类型；agent 层顺滑 | 起源系统(Origin) python 资产需翻译（约 2~3 天工作量，脚本逻辑简单可机器辅助） |
| B. Python | 现有资产直接抽包；测试团队熟 | 与 e2e/UI 层割裂，契约类型无法共享，长期两头维护 |

---

## 决策建议

**做，但分三步走（避免 n=1 过度设计）：**

| 步骤 | 时机 | 动作 | 风险 |
|---|---|---|---|
| **第一步：抽包** | 立即（1~2 周） | 把起源系统(Origin) python 资产提炼为内部库 `qa-kit`（req 封装/错误码断言/勾稽原语/基线四步/报告生成器）——纯抽包，零新设计 | 无 |
| **第二步：立框架** | 下个系统（CRM/MES）启动时 | 按 L1~L5 搭 v0.1：契约驱动 + 旅程模板 + 三通道；用第一个真实系统验证泛化边界（此时 n=2，抽象有依据） | 中：需 P0 前提到位 |
| **第三步：接 agent** | 拿到模型 API key 后 | agent.act 录制回放接入，复杂路径成本趋零 | 低 |

**向设计侧发出的硬要求（现在就可以发）**：从下一个系统起，交付物必须包含 P0 三件套（OpenAPI / 错误码枚举 / 角色矩阵账号），P1 两件（环境重置 / 不变量表）列入验收标准——这比框架本身更重要：**可测性是被测系统设计出来的，不是测试团队测出来的。**

*分析基于起源系统(Origin)全部测试档案（内部档案目录 等）与 e2e v0.15.1 源码 · 2026-10-03*
