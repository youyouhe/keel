# Keel 契约规范 v0.1（六件套）

> 契约是判断对错的标尺。可执行、进 git、随 PR 演进——否则必然腐烂。
> 示例以 CRM / MES 跨域对照编写，证明骨架通用。

## 目录结构

```
contracts/
├── openapi.yaml        # API 契约（或从代码生成的 TS 类型包）
├── error-codes.yaml    # 错误码枚举: code/httpStatus/meaning/trigger
├── roles.yaml          # 角色 × 权限点矩阵（含数据权限 dataScope）
├── invariants.yaml     # 业务不变量（守恒律）★灵魂文件
├── journeys/           # 旅程实例（泛化 9 段骨架）
├── seed/               # 种子数据集（版本化）
└── CHANGELOG.md        # 契约变更日志（谁/何时/为何）
```

## error-codes.yaml（跨域同构示例）

```yaml
# —— 通用模式：状态机拒绝 ——
- code: PERIOD_CLOSED
  httpStatus: 409
  meaning: 生命周期阶段已锁定（结账/业绩锁定/期间冻结）
  trigger: 目标期间已关账
# ERP: 闭期拒制单 | CRM: 已锁定业绩期拒改 | MES: 已冻结期间拒工单变更

# —— 通用模式：岗位分离 ——
- code: SELF_AUDIT_DENIED
  httpStatus: 400
  meaning: 操作人与发起人不得为同一人
  trigger: auditor == creator
# ERP: 制单≠审核 | CRM: 提单≠审批 | MES: 报工≠质检确认

# —— 通用模式：引用保护 ——
- code: ENTITY_REFERENCED
  httpStatus: 409
  meaning: 已被引用的实体不可删除
# ERP: 已引用档案 | CRM: 有商机的客户 | MES: 已领料工单

# —— 通用模式：守恒违例 ——
- code: NEGATIVE_STOCK          # ERP: 负库存 | MES: 超产
  httpStatus: 400
- code: QUOTA_EXCEEDED          # CRM: 折扣/额度超限
  httpStatus: 400
```

## invariants.yaml（守恒律——每系统由设计侧声明）

```yaml
- id: INV-LEDGER-BALANCE        # ERP 实例
  rule: 试算三层平衡（期初/发生/期末）
  check: trial_balance.check.{initialDiff,closingDiff} == 0
  version: 1
  status: confirmed             # confirmed=实测通过 | unsourced=待拍板

- id: INV-PIPELINE-CONSERVED    # CRM 实例
  rule: 各阶段商机金额之和 = pipeline 总额；回款累计 ≤ 合同额
  check: sum(stages) == total && payments.sum() <= contract.amount
  status: draft

- id: INV-MATERIAL-BALANCE      # MES 实例
  rule: 物料守恒 投入 = 合格 + 不合格 + 损耗
  check: input.qty == ok.qty + ng.qty + loss.qty
  status: draft
```

## journeys/（泛化 9 段骨架）

```
J0 越权与多租户 → J1 主数据建账守卫 → J2 档案域 → J3 业务单据循环(多线)
→ J4 周期关账(状态机) → J5 季度/年度汇总 → J6 跨期承接
→ J7 报表勾稽 → J8 次年/次期初始化 → J9 审计穿透
```

每系统一份 journeys 实例：骨架段固定，段内步骤与断言由领域插件填充，断言锚定 invariants/roles 的条目 id。

## 演进机制（防腐烂四则）

1. **同 PR 流转**：改行为的 PR 必须同时改契约；CI 校验契约-实现一致
2. **变更分级**：加字段=minor；改语义/删字段=major（CI 报受影响用例）；**不变量变更=业务规则变更，强制评审**
3. **运行时漂移检测**：每次测试运行先验契约（端点在/错误码在枚举内/响应匹配 schema）
4. **所有权**：内容责任在设计侧（签收人制），形式与校验在测试侧（契约主编）；作者不得自任校验者

## 编写模式（AI 主笔、人主拍板、实测主校验）

```
AI 提出假设（带证据锚定：代码位置/API 实测/文档引用，标 confidence）
  → 实测系统验证（invariant 编译成断言真跑）
  → 通过 = confirmed 入契约 | 不通过/无法测 = unsourced 待专家拍板
```

专家的工作形态：从"写规则"（100h）变为"答 AI 选择题"（10h）——AI 列选项+trade-off+证据，人勾选并对口径负责。

## 争议仲裁

- 实现与契约不符 → 默认实现错（缺陷）
- 设计认为契约该改 → 走契约变更评审；旧版本不变量列入回归必测
