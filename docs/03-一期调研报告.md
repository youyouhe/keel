## 二、三条关键发现（改变决策的）

### 发现 1：Playwright 官方 agent 化，冲击 e2e 的核心卖点
微软双线投入：**官方 MCP server**（@playwright/mcp，a11y 快照驱动、无视觉模型）+ **Playwright CLI 专为 coding agent 设计**（宣称比 MCP 更省 token），仓库带 CLAUDE.md。这意味着"agent 驱动浏览器"将有基座级、资源最厚的实现——e2e 的差异化只剩**录制回放缓存**（且要等我们有模型 key 才用得上）。
**决策修订**：channel-ui 默认 **Playwright 原生（@playwright/test）**；e2e 从"现役"降为**观察项**（等 agent 回放需求真实出现时，再对比 e2e vs playwright-mcp）。起源系统(Origin)试点 11 条断言只用了 locator 层能力，平移成本 ≈ 改 import。

### 发现 2：Schemathesis 是"立即可用"的 L1→L2 引擎
四个直接命中：①从 OpenAPI 自动生成正/负例（含 probing/examples/fuzz 多相位）；②**状态化测试**（从 schema links 推断工作流——正是我们"旅程"的自动化雏形）；③**custom checks 可挂业务断言**（invariants.yaml 编译后的挂载点）；④LLM payload 生成（agent 化已内建）。
**决策**：采纳为 REST 通道的 fuzz+契约校验引擎，openapi.yaml 契约直接喂入；自研断言体系保留（业务语义层它不管）。

### 发现 3：Pact 的 Broker 是契约治理的成熟样板，但契约粒度不同
Pact 契约 = **接口 schema 级**（消费者期望的请求/响应匹配）；我们的核心契约 = **业务不变量级**（回款≤合同额、试算平衡）。互补不替代。
**决策**：不引入 Pact 代码；**抄治理机制**——契约版本化仓库、验证结果共享矩阵、"能否部署"门禁（对应我们"契约不过、发布不过"的 CI 闸）。

## 三、对五层架构的选型修订

| 层 | 原方案 | 调研后修订 |
|---|---|---|
| L1 契约层 | 自建六件套 | 不变；治理机制抄 Pact Broker（版本化+验证矩阵+部署门禁） |
| L2 REST 通道 | 自研 python 断言 | **+ Schemathesis 引擎**（fuzz/schema 校验/状态化），业务断言仍自研 |
| L2 MCP 通道 | 自研 tools/call | 不变 |
| L2 UI 通道 | e2e 现役 | **改 Playwright 原生**；e2e → 观察项；agent 化路线 = playwright-mcp |
| L3 原语层 | 自研 | python 栈则以 **pytest 为基座**（fixture/plugin）；Karate 的 match DSL 语法作表达力参考 |
| L4 旅程层 | 自研（EPF 泛化） | 不变（无现成可买）；Schemathesis links 状态化测试作局部补充 |
| L5 报告层 | 自研 | 不变 |
| 环境/seed | 待定 | **testcontainers**（CRM/MES 开发期起依赖） |
| Agent 层（可选） | e2e agent.act | **三路现成组件**：playwright-mcp（UI）+ Schemathesis LLM payload（API）+ Claude 会话（编排）——自研 agent 层需求大幅降低 |

## 四、采纳 / 观察 / 放弃三清单

- **立即采纳**：Schemathesis（REST 引擎）、Playwright 原生（UI 基座）、pytest（python 基座）、testcontainers（环境，按需）
- **观察**：e2e（回放缓存兑现时再评）、playwright-mcp（跟随微软节奏）、Karate v2（转型稳定后看断言 DSL）
- **放弃**：Pact 代码（抄思想）、k6/locust（SCALE 专项启动时二选一）

## 五、遗留判断点

1. 技术栈最终拍板（TS vs Python）仍待定——本调研让 Python 权重上升（Schemathesis/pytest/locust 同栈）；但若 CRM/MES 前后端均 TS，契约类型共享仍 favors TS。**建议 qa-kit 先以 python 出（零迁移成本），v0.1 时再定**
2. e2e 试点 11 断言是否平移到 Playwright——建议平移（半天），消除 pre-1.0 依赖
3. Pact Broker 思想落地形式（自建 SQLite/文件矩阵即可起步，不必上真 broker）

## 六、两项实战验证（同日完成）

### 6.1 e2e → Playwright 平移：11/11 全绿，21.0s
`内部档案目录/msp-playwright/`（@playwright/test + storageState 认证注入，断言自 e2e-pilot 原样平移，仅 tap→click）。**e2e pre-1.0 依赖正式消除**；channel-ui 决策修订坐实。平移成本 ≈ 改 import，半天预估实际 20 分钟。

### 6.2 Schemathesis 实战：8 秒 42 case，8 failure —— 三类真实缺陷
手写起源系统(Origin)逆向 mini spec（`msp-openapi-mini.yaml`：5 只读端点 + demo-login，写端点不进 spec 防污染）→ `st run --checks all`：

**真实发现（起源系统(Origin)缺陷清单追加，均 P3）**：
- **O-ST-1** `period=202613`（13 月）被 trial-balance 接受返回 200 且给出数据（幽灵期）——服务端月份校验缺失
- **O-ST-2** `page=0` / `pageSize=99999` 被 vouchers 接受——分页边界无校验
- **O-ST-3** `TRACE` 方法打业务端点返回 404 JSON 而非 405——HTTP 方法白名单缺失

**其余 5 个 failure 均为手写 spec 偏差**（响应实为数组写成 object、403/404 未在 spec 声明）——恰好实证 P0 契约前提的必要性：**没有官方 spec，连测试基准都不准**。

**方法论价值**：负例 fuzz 是人工测试覆盖不到的盲区（既往轮次从未测过 page=0/13 月）——Schemathesis 采纳决策从"调研结论"升级为"实战验证"。

**环境共管观察**：fuzz 输出中出现 period=202610（今日日期）的新凭证——开发侧 10-03 也在共管环境操作（新开 202610 期），环境漂移再现。
